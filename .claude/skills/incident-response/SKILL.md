# Incident Response

production이 부서졌을 때 따르는 절차. 머릿속 패닉을 시스템으로 대체합니다.

## 5단계

```
1. 분류 (Triage) — 30초
2. 완화 (Mitigate) — 우선
3. 근본 원인 (Root Cause)
4. 영구 수정 (Fix)
5. 사후 (Postmortem)
```

근본 원인 파악보다 **완화가 먼저**. "왜?"는 사용자 영향 멈춘 후에.

## 1. 분류 (30초 안에 결정)

심각도(severity) 분류:

| Sev | 정의 | 예시 | 대응 |
|---|---|---|---|
| **SEV1** | 사용자 다수가 못 씀 | 사이트 다운, 로그인 불가 | 즉시 대응, 모든 작업 중단 |
| **SEV2** | 핵심 기능 일부 망가짐 | 결제 실패 일부, 검색 안 됨 | 즉시 대응, 다른 작업 보류 |
| **SEV3** | 영향 작거나 우회 가능 | 비핵심 페이지 에러, UI 깨짐 | 영업 시간 안에 수정 |
| **SEV4** | 사용자 영향 거의 없음 | 내부 도구 에러, 로그 노이즈 | 다음 sprint |

**자율 시스템에서는 무조건 SEV1·SEV2면 사람 호출**. Claude는 정보 수집·완화 제안까지.

## 2. 완화 (Mitigate)

목표: **근본 원인 몰라도 사용자 영향 줄이기**.

옵션 (실행 빠른 순):
1. **Feature flag 끄기** (플래그가 있으면, 5초)
2. **롤백 — 이전 deploy로** (Vercel/Netlify·Render·Fly 등은 1클릭, 1-2분)
3. **트래픽 우회** (Cloudflare 메인터넌스 페이지)
4. **수동 데이터 수정** (망친 row 직접 UPDATE — 위험, 백업 후)
5. **외부 의존성 우회** (Stripe 다운이면 결제 비활성화)

**핵심**: 완화하면서 **타임라인 기록**. `replays/<date>-incident-<short>.md`:
```
HH:MM 알람 발생
HH:MM 분류 SEV2 (결제 실패율 30%)
HH:MM 가설 1: 새 deploy
HH:MM 롤백 시작
HH:MM 롤백 완료, 결제 정상화
```

타임라인은 사후 분석의 가장 중요한 데이터.

## 3. 근본 원인 (Root Cause)

완화 후 시간 여유 생기면:

### 5 Whys
- 왜 결제가 실패했나? → API 호출이 timeout
- 왜 timeout? → DB 쿼리가 30초 걸림
- 왜? → 인덱스 안 탐
- 왜? → 신규 컬럼에 인덱스 안 만듦
- 왜? → migration 체크리스트에 인덱스 항목 없음
→ **근본 원인**: 프로세스 결함

### 증거 수집
- 로그 (사고 시각 ±10분)
- 메트릭 (응답시간, 에러율, DB 부하)
- 최근 변경 (deploy, migration, config, 외부 의존성 변경)
- 에러 트래킹 (Sentry 등) 첫 발생 시각

### "근본"이 아닌 답 거부
- "쿼리가 느렸다" → 그건 증상
- "코드 버그" → 그것이 어떻게 머지됐나가 근본
- "사람 실수" → 시스템이 막았어야 하지 않나

## 4. 영구 수정 (Fix)

근본 원인에 대한 수정 + **재발 방지 시스템**.

| 근본 원인 | 영구 수정 예시 |
|---|---|
| 인덱스 누락 | 인덱스 추가 + migration 템플릿에 인덱스 체크리스트 |
| 환경변수 미설정 | startup에서 환경변수 검증, 누락 시 부팅 거부 |
| 외부 API 다운 | 회로 차단기(circuit breaker), graceful degradation |
| 코드 버그 | 수정 + 그 패턴 잡는 테스트 추가 + 같은 패턴 다른 곳 검색 |
| deploy 실수 | CI 체크 추가 + 배포 절차 문서화 |

**한 번 일어난 사고는 시스템으로 막아라**. 사람 더 조심하라는 결론은 무효.

## 5. 사후 (Postmortem)

24-72시간 안에 작성. 비난 없는 톤(blameless).

`replays/<date>-incident-<name>.md` 또는 `decisions.md` 항목:

```markdown
# Incident: <짧은 제목> (<date>)

## 요약
- 영향: <사용자 N명, M분>
- Sev: <1-4>
- 트리거: <무엇이 사고를 시작했나>

## 타임라인
HH:MM ...

## 근본 원인
<5 Whys 결과>

## 영구 수정
- [x] <즉시 수정>
- [ ] <시스템 개선> (#issue-link)

## 학습
<learnings.md에 한 줄 추가할 것>

## 무엇이 잘 됐나
<진짜로 — 모니터링이 빨리 잡았다, 롤백이 빨랐다 등>

## 무엇이 더 빨랐어야 했나
<자동 알람 누락, 수동 단계가 많았다 등>
```

## 자동화 정책

- **자율 시스템은 SEV1·SEV2 발생 시 즉시 멈추고 사람 호출** (notify webhook)
- 완화 옵션은 **제안**까지 (롤백·플래그 끄기는 자동 OK 설정 가능)
- 영구 수정과 사후는 사람과 함께

## 사람 호출 트리거

- 에러율 > 5% 30초 이상
- 응답시간 P95 > 평소의 3배
- 결제 성공률 < 95% (5분간)
- 보안 이벤트 (시크릿 노출, 인증 우회)
- DB 마이그레이션 실패
- 한 번에 100명 이상 영향
