# TDD Workflow

테스트가 코드보다 먼저 명세 역할을 하게 하는 절차. AI가 코드 짜기 전에 동작이 무엇이어야 하는지 강제로 정의하게 만듭니다.

## 사이클: Red → Green → Refactor

### Red: 실패하는 테스트 작성
1. 한 번에 하나의 동작만 테스트
2. 가장 작은 케이스부터 (happy path)
3. 명확한 입력·출력 명시
4. 실행 → 빨간색 (실패) 확인

테스트가 통과하면 잘못 작성된 것:
- 이미 구현되어있다 (다른 케이스 필요)
- 테스트가 검증을 안 한다 (assertion 없음)

### Green: 가장 작은 코드로 통과
- 하드코딩이라도 OK (다음 테스트가 강제로 일반화시킴)
- 다른 테스트 깨뜨리지 않기
- 통과시키는 데 집중, 우아함은 다음 단계

### Refactor: 통과 상태에서 정리
- 중복 제거
- 이름 개선
- 함수 분리
- **각 변경 후 전체 테스트 재실행** (회귀 방지)

## 테스트 작성 순서

```
1. 단순한 happy path (1개 입력 → 1개 출력)
2. 두 번째 happy path (다른 입력)
3. 경계값 (빈, 0, 1, 매우 큰 값)
4. 에러 케이스 (잘못된 입력 → 명확한 에러)
5. 통합 (DB·API·외부 서비스와의 상호작용)
```

각 단계마다 사이클: Red → Green → Refactor.

## 좋은 테스트의 특징

- **이름이 명세**: `should_return_403_when_user_is_not_admin` (X: `test_auth`)
- **하나의 행동 검증**: 한 테스트 = 한 assertion 그룹
- **독립**: 다른 테스트 결과·실행 순서에 영향 없음
- **빠름**: 단위 테스트 < 100ms
- **결정적**: 시간·랜덤·외부 상태 모킹

## 실효성 검증 (Mutation Mini)

테스트 작성 후 다음 1-2분 투자:

1. 코드 한 줄 의도적으로 깨뜨림:
   - `return x + y` → `return x - y`
   - `if (a > b)` → `if (a >= b)`
   - `for i in range(n)` → `for i in range(n-1)`
2. 테스트 실행 → 잡으면 OK, 통과해버리면 그 테스트 부족함
3. 원복 후 테스트 보강

이걸 안 하면 "통과하지만 아무것도 검증 안 하는 테스트"가 누적됨.

## 모킹 가이드

**모킹 대상**: DB, HTTP API, 파일 시스템, 시간, 랜덤
**모킹 안 함**: 같은 모듈 내 함수, 순수 함수

테스트가 모킹으로 가득하면 설계가 잘못됐다는 신호. 의존성 주입 고려.

## TDD가 안 어울리는 경우

- UI/디자인 탐색 (먼저 만들고 나중에 테스트)
- 한 번 쓰고 버릴 스크립트
- 외부 시스템 통합 (먼저 작동시키고 후에 mock으로 회귀 테스트)

이 경우엔 통합 테스트만 짧게 작성.

## 출력 (이 skill 완료 시)

1. 추가된 테스트 목록 (이름만)
2. 커버리지 변화
3. mutation 검증 결과 ("3개 케이스 중 3개 잡힘")
4. 다음에 작성할 테스트 후보 (선택)

## 자주 하는 실수

- 한 번에 여러 동작 테스트 → 디버깅 어려움
- 구현 디테일 테스트 (private 함수, 내부 상태) → refactor 깨짐
- 모킹 과도 → 진짜 통합 깨져도 통과
- 테스트 데이터 하드코딩 → 변경 시 다 깨짐 → factory/builder 패턴
