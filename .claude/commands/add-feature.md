당신은 시니어 엔지니어입니다. `$ARGUMENTS` 기능을 다음 순서로 추가하세요.

## 1. 명세 (Spec)

명확한 요구사항이 없으면 다음 7개 질문에 스스로 답하고 사람 확인 받기:
1. 사용자 시나리오 (누가 / 언제 / 왜)
2. 입력·출력 정확한 형태
3. 에러 케이스 (네트워크 실패, 권한 부족, 잘못된 입력)
4. 성공 기준 (기능적 / 성능)
5. 영향 범위 (DB 스키마, API 계약, UI)
6. 비기능 요구사항 (보안, 권한, 감사 로그)
7. 마이그레이션 (기존 데이터·사용자 처리)

## 2. 설계 (Design)

- `decisions.md`에 결정 기록:
  - 선택한 접근, 대안, 이유
- 변경 영향 범위가 크면(>5 파일, DB 마이그레이션, API 변경) `plans/feature-<name>.md`로 분리:
  - 작업 단위 분해
  - 각 단위의 테스트 전략
- **여기서 멈추고 설계를 사람에게 보고**.

## 3. 구현 (Implement)

- 기존 컨벤션 따름 (CLAUDE.md, 인접 코드).
- 작은 커밋 (1 커밋 = 1 논리 단위).
- 외부 의존성 추가는 `decisions.md`에 이유 기록.

## 4. 테스트 (Test)

- 신규 코드는 반드시 테스트 동반.
- 단위 테스트 + 가능하면 통합 테스트.
- 에러 케이스 테스트 (1번 명세에서 식별한 것).

## 5. 문서 (Document)

- 사용자가 보는 기능이면 README 또는 docs/ 갱신.
- API 변경이면 OpenAPI/타입 갱신.
- 환경변수 추가 시 `.env.example` 갱신 (실제 값 아님).
- PR 본문: 명세 1번 + 스크린샷 + 테스트 방법.

규칙:
- 명세 없이 코딩 금지.
- "AI가 제안한 라이브러리"를 검증 없이 추가 금지 (npm/PyPI 페이지 확인).
- 테스트 없이 머지 금지.
